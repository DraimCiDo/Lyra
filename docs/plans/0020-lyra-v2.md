# Lyra v2 development plan

Status: implementation and preview verification in progress.

Reference revision: Lyra `main` at `e953c00771652efc7e7654e939755f6ac0e356a5`.

AI Playbook: `0.1.1`, `default` profile, source revision `36523876f9971a764442c54b2fb32678ea9530e8`.

## Outcome and scope

Rebuild Lyra around one reliable local coding workflow on Windows 11 x64. A user opens a project, selects a GGUF, describes a task, sees progress, reviews a diff alongside independent check results, and explicitly applies the proposal. Chat works offline with a prepared model. The same task submitted from Desktop and CLI follows the same rules and produces equivalent results.

Keep the v1 release line and its data usable during development. Build v2 in the existing repository, with separate build targets and a separate data directory while both versions coexist. Treat the stage list as proposed scope. Approve the runtime and persistence architecture before building dependent code, and approve any dependency or schema changes explicitly.

## Performance target

Accept Lyra on RTX 2060 and RTX 4060 with their actual VRAM recorded. Use unmodified NVIDIA
drivers for the baseline. Treat any pre-boot tensor-rate experiment as a separate A/B on the
same machine, GPU, model, quantization, context, prompt and power limits. Record prompt tokens
per second and generation tokens per second separately, and measure the time and success rate
for a complete checked change. Establish release budgets after the first hardware baseline.

| Workload | Reproducible acceptance |
| --- | --- |
| DraimHorizon | Pin `DraimCiDo/DraimHorizon` at `084b059ed468edee7230b2a6f139a8a38722757a` for the initial baseline. Start with a navigation or schematic regression that crosses module boundaries. Run the relevant Rust tests and the affected Horizon/Sunrise packaging checks. |
| Game modding | Pin a game, mod loader and SDK. Change behavior across a source file and configuration or asset, build the mod, then verify loading and the changed behavior in the game or an integration fixture. |
| Game from scratch | Pin an engine and create or extend a small playable project. Verify export, startup and one complete gameplay loop. Record engine or SDK prerequisites with the result. |

The pinned DraimHorizon checkout has 499 tracked files and about 6.9 MiB of tracked worktree
files. `mixins/draimhorizon/menu.rs` alone is 482,553 bytes. The old 256 KiB interactive read
limit could block discovery in this file. v2 supports paged reads on larger text files and
directory-scoped search. Large-file proposals still use whole-file text and are limited by
the current edit and report budgets. Replace that bottleneck with bounded edit ranges before
counting large-file edit scenarios as accepted. For projects beyond the index or snapshot
budget, measure scoped discovery and an isolated checker for the affected modules.

For each representative workload use at least three runs per hardware and model profile.
Record repository and toolchain revisions, the model hash, offloaded layers, peak RAM/VRAM,
retrieval time, cold/warm first-token delay, prompt throughput, generation throughput, total
time to checked result, check outcome and task completion. Compare against the pinned
baseline and count source preservation and correctness before speed.

## Baseline

- v1 already has Rust CLI and egui Desktop, local GGUF, opt-in HTTP, SQLite checkpoints, explicit apply with recovery, GitHub and a code graph. The rewrite can use its fixtures, published contracts and acceptance criteria as references.
- Today the agent combines model actions, a local grammar and orchestration in `src/agent.rs`. Desktop has a worker and a text progress protocol in `src/desktop/job.rs`. Desktop history and preferences have separate persistence from the task database. These are concrete boundaries to review when designing the shared runtime.
- The repository documents narrow successes with real 7B/9B models. It also includes a 36-task corpus with 30 unit-checked tasks and 6 structural checks. Neither establishes everyday quality on the owner's Windows machine. Record the failures that motivated the rewrite from 2–3 real tasks and keep them as regression cases.

## Proposed architecture

- **Task runtime.** One typed request, action, result and event contract for CLI and Desktop. A persisted task has explicit states for running, waiting for approval, ready to apply, failed, cancelled and applied. The report records verification separately, including passed, failed, unavailable and skipped. Persist events needed for recovery and reconcile interrupted actions before retrying.
- **Model boundary.** Use Rust for the runtime and keep GGUF via llama.cpp as the first adapter. Exercise the runtime with a deterministic fake model and separately with a pinned real model. Measure cold load, time to first token and cancellation before deciding whether model reuse needs a separate process. Keep egui for the first Windows acceptance unless a prototype demonstrates a concrete blocker.
- **Workspace and checks.** The model proposes typed actions. The application validates scope and permissions against the selected workspace. Build the patch in isolation, run the user's configured checker against that exact candidate, and tie the result to the diff. Apply verifies the base again, preserves concurrent user edits, and journals partial writes for recovery. Default to offline inference, restrict check execution to the configured isolated environment, and report unavailable isolation explicitly.
- **Desktop and CLI.** Desktop shows one visible flow from task to result, with the selected project/model, progress, cancel, diff, check output and Apply in context. CLI consumes the same runtime and emits a structured report. Keep diagnostic, verification and apply behaviors testable without the GUI.
- **Persistence.** Propose a separately versioned store with a read-only v1 import for supported history and preferences. Preview counts and unsupported records, maintain the v1 source, and make import idempotent. Old pending reports, journals and checkpoints remain recoverable through v1 until explicit compatibility is designed. Credentials are reconfigured through the v2 credential path.

## Milestones and exit criteria

| Stage | Work | Exit evidence |
| --- | --- | --- |
| M0. Baseline and decisions | Freeze the comparison revision, reproduce the owner’s recurring failures, and agree on the initial matrix, Windows configuration and release budgets. Start with `examples/buggy-add`. | Baseline checker fails, the candidate and applied copy pass the same independent check, and the source is unchanged until apply. | M2. Native Desktop beta | Drive the same task from Desktop. Add local chat, GGUF selection, progress, cancel, result view and recovery. | Run offline on a real Windows 11 x64 machine with a prepared GGUF. Verify cold/warm start, first token, cancel, restart, unchanged source before Apply, and a conflict caused by an intervening user edit. |
| M3. Quality and migration | Measure failures, context exhaustion and repeated tool calls. Improve the weakest observed parts. Add preview and repeatable import for the supported v1 data. | Every agreed must-pass regression succeeds. Same-hardware comparisons meet M0 thresholds. Repeated import creates no duplicates, leaves v1 data intact and reports partial failures. |
| M4. Integrations and portable RC | Add opt-in HTTP, GitHub issue to draft PR, Graphify, and opt-in subagents behind the stable task contract. Package and test on a clean Windows machine. | Verify real GitHub and Graphify with an approved test repository, retain the manual approval gates, and run the package without a Rust or Python install for core scenarios. |

Proposed previews ship after M2 and M3. M4 meets the current repository's release-candidate scope. Broader ECC/OmniRoute parity, MCP/hooks, memory and learning, advanced routing, Office/PDF and multimodality each need their own priority decision. GPU acceleration has a separate hardware acceptance track. Existing updater and release compatibility get a targeted review before changing the stable channel or release packaging.

## Release measurements

- Fix the repo snapshots, checker versions, model hashes, parameters, hardware and timeout across v1 and v2. Start with the simple defect, a multi-file case and a real owner task. Run three attempts per representative case and publish each outcome. Expand into the existing independently checked corpus once the vertical slice works. Report structural checks separately.
- Count task success only when the baseline fails, the scoped candidate passes the independent checker, and the applied result passes again. Track protocol completion, incorrect success, checked success, out-of-scope edits, retries and infrastructure blocks. A release-blocking invariant is zero unauthorized workspace modifications in the acceptance scenarios.
- Measure model cold load, first token, time to a checked proposal, peak RAM/VRAM and cancellation latency. Report measurements per hardware configuration and use the wider corpus for tail percentiles. Set numerical thresholds after the baseline.
- Keep Linux and Windows CI for deterministic verification. Proposed release checks are `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and the `cargo test --workspace --locked` matrix for default, `desktop` and `desktop,gateway-http`. Final commands must match the approved v2 target layout and feature names. Native Windows, Docker and live integration checks have their own evidence.

## Delivery and handoff

Keep each approved milestone on one task branch with one draft PR. The PR records Problem, Changes, Verification and Risks. Approve the exact checks and environments for each milestone before execution. Preserve the v1 download and data through the v2 preview sequence. Release approval follows native acceptance and the upgrade/rollback rehearsal.

Start M0 by reproducing the failures on the pinned v1 checkout and turning them into acceptance cases. Draft the runtime and persistence decisions from that baseline before the first v2 code commit. Candidate first development commits are `test(eval): capture v1 regression cases` and `docs(architecture): define v2 runtime boundaries`.

## Implementation and evidence

- The existing workspace and isolated check executor underpin the v2 runtime. The CLI and Desktop use the separately versioned task report and its atomic checkpoints. The v1 app and release build remain available.
- The initial comparison uses the single-file `examples/buggy-add` regression and the existing Python and backend/Rust fixtures. Host validation passed all 60 checks across 18 trusted fixture cases, including baseline, reference and per-file reversion checks. Host validation does not execute model output. Model comparison uses the same pinned Docker check via `tools/evaluate.py --protocol v1|v2` with `--case` to select identical cases.
- The local Docker daemon fails Lyra's isolation preflight. The independent Docker acceptance runs in the Linux CI job. GitHub Actions also builds both Windows v2 executables, performs a native startup smoke test and archives a separate preview artifact.
- A local CPU run of Qwen2.5-Coder 0.5B Instruct Q4_K_M (SHA-256 `1d9614638d18024d0fbb36575a15f1302a3adf044df10345688ec4f6e1c4ff32`) reproduced a repeated-edit loop on `buggy-add`. After the fix it returned the exact expected patch in three calls and 42.8 seconds on this Linux worker. The original was unchanged before explicit Apply, and the applied bytes matched the reference. Verification was reported as skipped in this run, which did not execute model output.
- Graphify 0.9.115 ran on the `buggy-add` fixture through Lyra's shared adapter. The imported graph contained six nodes and seven edges.
- User-reported regressions, an owner-machine Windows 11 run, and the end-to-end GitHub issue-to-draft scenario in an approved test repository are open acceptance evidence. The model performance gates require comparable measurements on the target configuration.
