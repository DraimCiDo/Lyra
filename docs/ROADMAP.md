# Дорожная карта

Каждый этап выполняется отдельной задачей. Этот документ не означает разрешение
сразу реализовать все перечисленные функции. Основа — в [плане M0](plans/0001-repository-foundation.md),
текущая alpha — в [плане](plans/0004-testable-agent.md).

| Этап | Содержание | Критерий завершения |
| --- | --- | --- |
| M0 — основа, завершено | GitHub-репозиторий, README, AGENTS.md, выбор языка и границы MVP. | Документы согласованы, ссылки проверены, начальный коммит отправлен в `main`. |
| M1 — CLI и диагностика, завершено | Cargo-проект, закреплённый toolchain, help/version/doctor, ошибки вывода, Linux/Windows CI. | Прошли тесты и Windows MSVC CI; есть EXE и baseline Linux. Приёмка на Windows 11/GPU пользователя отмечается отдельно. |
| M2 — локальная модель: CPU готов, CUDA не проверена | Локальный GGUF/runtime, CPU/CUDA, явная модель, streaming, лимиты и отмена без обязательного сервера/API. | Работа с подготовленными весами без интернета; проверены загрузка, генерация, память и отмена; CPU-тесты отделены от Windows/GPU-прогона. |
| M3 — alpha контекста/инструментов; OS sandbox остаётся | Чтение/поиск, AGENTS.md, патчи, политика доступа, решение и реализация Windows sandbox, разрешённые команды. | Проверены конфликты/CRLF/Unicode, отказ и границы доступа, таймаут и завершение дочерних процессов. |
| M4 — MVP для кодинга | Общий цикл «задача → контекст → патч → тест → отчёт». | На тестовом репозитории агент исправляет дефект, показывает diff и результат теста; чужие изменения сохранены; выполнена нативная Windows-приёмка. |

Приёмка M3 обязательна до включения произвольных команд модели в поставку.
Сборка приложения без неё не означает готовность инструмента исполнения.

## После MVP

Возможные отдельные задачи: TUI, сохранение/возобновление сессий, другие
локальные backend, MCP, интеграция с редакторами, расширение GUI и функции
вне кодинга. Приоритет выбирается по реальному использованию первого MVP.

## Открытые решения

- Конкретная локальная модель/runtime, контекст, параметры GPU/CPU и бюджет памяти.
- Механизм изоляции Windows и требуемая им версия ОС.
- Версии Rust/зависимостей и численные бюджеты производительности.
- Формат пользовательского конфига и хранения сессий.
- Лицензия проекта и будущая подпись/публикация поставок; portable Windows CPU
  и обновления GitHub Releases уже описаны в [UPDATES.md](UPDATES.md).

Эти решения фиксируются в соответствующей задаче до добавления зависимого кода.

Подагенты продукта уже входят в тестируемую alpha как опциональный последовательный pipeline с одной моделью. Автономный shell и полная приёмка на 7B/CUDA ещё не завершены.

Настольная alpha реализована отдельным optional feature `desktop`: нативный EXE,
проект/GGUF/задача, отмена, предложения и явный apply.
[Запуск и ограничения](DESKTOP.md), [план и доказательства](plans/0005-desktop.md).
Это интерфейс существующего движка; M4 с автоматическим запуском тестов
и приёмкой качества модели остаётся отдельным этапом.

В `0.2.0-dev.4` добавлены универсальный blueprint нового проекта, предпросмотр
и отдельное создание; локальные document packs и `search_docs`, явная загрузка
официальных источников и предложения новых файлов в существующих проектах.
Проверки и ограничения — в [плане этапа](plans/0008-projects-knowledge.md).
Это не завершает M4: приложение пока не запускает сборку произвольного AI-проекта.

## Предлагаемый порядок улучшений

1. **Изолированные проверки.** Выбрать механизм Windows sandbox, затем добавить
   явный запуск разрешённых сборок/тестов с ограничением времени, вывода, файлов,
   сети и дерева процессов. Проверять поведение недоверенного build-кода.
2. **Измерение качества.** Набор одинаковых задач на исправление дефектов,
   создание проектов и использование версионного SDK. Оценивать прохождение
   независимых тестов, сохранность файлов, память и время; отдельно сравнить
   одну роль с подагентами и разные локальные GGUF. Сравнение с GPT требует
   того же задания и критериев, а не субъективной оценки ответа.
3. **Профили ресурсов.** Измерить CUDA/контекст на пользовательском ПК, показать
   расход памяти и ограничения до старта. Выбор модели остаётся явным;
   автоматическое переключение или облачный fallback не подразумеваются.
4. **Более точный контекст.** По результатам задач расширять версионные источники,
   поиск по API-символам и обновление локального индекса по изменённым файлам.
   Не загружать весь репозиторий или документы в каждый запрос.

Подобный [OmniRoute](https://github.com/cheaper-inference/OmniRoute) gateway
может стать отдельным слоем адаптеров готовых моделей
с явным выбором локального backend. Он не обучает новую модель и сам по себе
не повышает качество генерации. Внешние providers потребуют отдельного решения
пользователя; сейчас их, маршрутизации запросов и скрытого fallback в Lyra нет.
