# GitHub-коннектор и проверка подагентов

Требует feature `gateway-http` (`cargo build --release --features gateway-http`).
Токен читается из переменной окружения (по умолчанию `GITHUB_TOKEN`, имя меняется
`--token-env`); он не передаётся аргументом, не хранится и не пишется в вывод.
`--api-url` допускает только HTTPS (loopback HTTP — для тестов/прокси). Редиректы отключены.
Всё, что пришло с GitHub, — недоверенные данные: текст issue/PR передаётся задаче
как цитата без прав.

## Команды `lyra github`

| Команда | Действие | Запись |
| --- | --- | --- |
| `issue --repo o/r --number N [--out task.txt]` | issue + комментарии; `--out` создаёт файл задания | нет |
| `issues`, `pulls` | списки открытых issue / PR | нет |
| `pull --repo o/r --number N [--diff] [--out task.txt]` | PR, файлы, diff; `--out` — задание на ревью | нет |
| `file --repo o/r --path p [--ref b]` | файл удалённого репозитория (UTF-8) | нет |
| `comment --repo o/r --number N --body …` | комментарий | да |
| `publish --repo o/r --workdir DIR --report r.json --branch b [--base main] --title …` | ветка + коммиты по файлам + draft PR из предложений отчёта | да |

`publish` перед записью сверяет каждый существующий файл базовой ветки с
`original` предложения (расхождение — конфликт, ничего не создаётся), требует
`status=completed` и совпадение `workdir` с отчётом, отказывает при неудачной
последней проверке без `--allow-failed-checks`. PR открывается черновиком (`--ready` — обычным).

Сценарий: `github issue --out task.txt` → `task --check "cargo test" --subagents`
→ просмотр предложений → `github publish` → ревью человеком.

## Проверка предложений (`task --check`)

`--check "cargo test"` (повторяемый, также поле «Проверки» в настройках Desktop).
Команда делится на аргументы без shell; программа из фиксированного списка
(cargo, npm, pnpm, yarn, pytest, python, python3, go, dotnet, node, make, gradle, mvn, tsc).
Модель команду не выбирает. Проверка идёт во **временной копии** проекта
(без `.git`, `target`, `node_modules`, символьных ссылок) с применёнными предложениями;
реальные файлы не меняются. Лимиты: таймаут (`--check-timeout-secs`), 20 000 файлов / 256 МиБ,
вывод — первые 3 и последние 5 КиБ, дерево процессов завершается по таймауту.

Если проверка падает, предложения возвращаются кодеру (`--repair-rounds`, по умолчанию 2,
до 4 вызовов на раунд сверх `--max-calls`) вместе с выводом ошибки и прежними
предложениями; затем ревьюер видит итоговый результат. Результаты — в `checks`
отчёта (schema v4), роль `tester` в событиях.

**Ограничения:** это не песочница ОС — команды (и код проекта) выполняются с правами
пользователя; включайте `--check` только для проектов, которым доверяете. Проверка
доказывает лишь то, что покрывает набор тестов проекта. Качество решений зависит от модели.
