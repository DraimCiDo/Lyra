# Проверки и checkpoints задач

Рабочие блоки [программы качества](plans/0018-quality-workflows.md).
CLI поддерживает изменяемые предложения, обратную связь reviewer → coder,
явные Docker-проверки и опциональные SQLite-checkpoints. Это не завершенная
приемка сложных проектов или полная реализация программы.

## Правки и результат

`propose_edit` работает относительно текущего предложения файла, если оно есть.
`read_file`, `search` и `list` используют один pending-набор, включая новые файлы; исходный файл сохраняется как
предусловие `apply`. `discard_proposal` отзывает предложение без записи на диск.
Reviewer может вызвать `request_changes`; coder исправляет pending-версию,
затем reviewer проверяет повторно. Не более двух repair rounds и общего бюджета
`--max-calls` (1–256, default 48). Четыре подряд одинаковых action/result
останавливают задачу как `no_progress`; два синтаксически неверных JSON допускают
восстановление. Неизвестные инструменты/поля не исполняются.

Отчет v4 сохраняет `status` для совместимости и добавляет `outcome`:
`incomplete`, `analysis_complete`, `changes_proposed`, `changes_verified`.
Последний означает только успешную явно заданную проверку текущего набора
предложений. Полнота тестов и правильность требований не гарантируются.
В Desktop controller facts (число предложений и подтвержденные проверки)
показываются до комментария модели. Нулевой набор обозначается явно как
«Изменения не подготовлены», независимо от уверенности model summary.
Мнение reviewer по-прежнему не является доказательством теста.
Отмена/deadline проверяются до и после model/tool вызова; поздний `finish`
не превращает отмену в успех. Коды CLI: 130 — отмена, 124 — timeout,
включая HTTP task. Ожидание blocking HTTP остается кооперативным.
Отчеты v1–v3 поддерживаются apply; новые отчеты требуют новой Lyra.

## Применение набора и восстановление

```sh
lyra apply --repo ./project --report ./report.json --all
lyra recover --repo ./project
lyra recover --repo ./project --action rollback
# Либо завершить оставшиеся правки:
lyra recover --repo ./project --action complete
```

`--all` и `--index N` взаимоисключающие; старый вызов с `--index` сохранен.
До первой записи проверяются **все** выбранные предложения (до 8), исходное
содержимое, read-only, policy, дубликаты и пересекающиеся пути. Текущие dirty-файлы
допустимы, если совпадают с исходником предложения. Блокировка `.lyra/apply.lock`
сериализует CLI apply/recover этого проекта; файл остается, OS lock освобождается
при завершении процесса. Сторонние редакторы этой блокировке не подчиняются.

Перед заменой исходников синхронизируется `.lyra/apply-journal.json` с оригиналами
и предложениями. Он содержит приватный код: каталог `.lyra/` следует исключить из
Git и резервировать согласно политике проекта. На Unix новый журнал/lock имеют
права 0600; на Windows действуют унаследованные ACL каталога проекта.
После успеха журнал удаляется; обычная ошибка запускает попытку отката.
При сбое отката или завершении процесса журнал сохраняется и блокирует следующее
применение, включая Desktop `--index`, пока не выполнен `recover`.

`recover` без action только показывает пути и состояния без исходного кода.
`rollback` возвращает исходные файлы и удаляет созданные; `complete` дописывает
оставшиеся предложения. В обоих случаях весь набор сверяется до первой записи:
каждый файл должен совпасть с исходником или предложением. Любое внешнее содержимое,
symlink/junction или недопустимый путь блокирует операцию без перезаписи этой правки.
Для конфликта сначала сохраните внешние изменения отдельно и сопоставьте их с
журналом; не удаляйте журнал, пока не восстановлена согласованность набора.

Это последовательная публикация с undo, **не атомарная замена всего дерева**.
Сторонний процесс может увидеть промежуточное состояние. При конкурентной записи
после preflight часть файлов может остаться примененной, но журнал сохраняется.
После rollback могут остаться пустые каталоги. Гарантия относится к завершению
процесса, не ко всем сбоям диска/питания; поврежденный журнал не исполняется.
На Windows создание нового файла использует CREATE_NEW: завершение процесса
внутри записи может оставить неполный новый файл. Он не признается нашим по
совпадению префикса: recovery блокируется до ручной проверки/сохранения этой
версии. Полные оригиналы и предложения остаются в журнале. Существующие файлы
заменяются через предварительно синхронизированный временный файл.
Незавершенный staging без основного журнала означает, что запись исходников еще
не началась; recovery может удалить его. Desktop поддерживает применение всего набора и окно recovery;
состояние читается через тот же CLI, исходники в окне recovery не выводятся.

## Явная проверка Docker

Docker нужен только для этого режима; запуск обычного CLI/GGUF остается нативным.
Нужны Linux containers и заранее установленный образ с `/usr/bin/timeout`.
Образ задается неизменным digest, сеть и автоматический pull запрещены.
Образ проверяется до запуска: объявленные VOLUME допускаются только в `/tmp`
и `/source`, где их заменяют ограниченный tmpfs и read-only bind mount. Другие
тома, включая вложенные, блокируются. Proxy environment явно очищается.
Пути с запятой не поддерживаются Docker bind mount и явно отклоняются.

Проверенный пример `evals/python-multifile/check.json` использует pinned
официальный Python image. Его явная подготовка:

```sh
docker pull python@sha256:ae14d4ce8771606477a81446e7ef429edd6762305fc50c84507c1041fa8285d1
lyra verify --repo ./evals/python-multifile/source --config ./evals/python-multifile/check.json
```

Исходный fixture должен провалить assertion. Конфигурация задает program/argv,
image, timeout и memory; это доверенный выбор пользователя, не вывод модели.
Она может содержать независимые проверки, которые не передаются модели.
Контейнер получает копии только разрешенных UTF-8 файлов. Исходники и root FS
read-only, сеть отключена, capabilities сняты, no-new-privileges включен.
Нет host credentials, сокетов, Docker socket и произвольных host mounts.
Запись разрешена в ограниченный `/tmp`; `CARGO_TARGET_DIR=/tmp/target`.
Измененные предложения подставляются в копию перед проверкой, без записи оригинала.
Лимиты: 2 CPU, 128 процессов, 128–16384 MiB RAM, 64 KiB каждого потока вывода.
Постоянное Docker-логирование отключено (`--log-driver=none`).
Отмена/таймаут удаляют контейнер; без подтвержденной очистки проверка не успешна.
Внутренний timeout ограничивает выполнение даже при аварийном завершении Lyra.

```sh
lyra task --repo ./project --model /path/to/model.gguf --task-file ./TASK.txt \
  --check-config ./trusted-check.json --max-calls 48 --timeout-secs 1800
```

В этом режиме coder получает `verify` без параметров. Он не выбирает image,
argv или права. Ошибки доступны для исправления; завершение без успешной проверки
текущих предложений дает `verification_required`, и apply отказывает.
SHA256 связывает результаты с конкретными предложениями. Любая последующая
правка делает прежний результат недостаточным для завершения.

Это первый backend: Windows VM/SDK, установка зависимостей, profile adapters,
полные toolchains/сети SDK еще не реализованы. В Desktop можно выбрать готовый
check-config; его выполнение использует тот же CLI backend.
Индекс ограничен 8192 разрешенными путями и 100000 просмотренными записями.
В prompt попадает до 128 ранжированных/недавно найденных путей; модель использует
`list_files(prefix, offset)` (64 пути) и `search_page(query, offset)` (32 файла,
до 32 совпадений) для продолжения. `search`/`list` сохраняют совместимость как
первые страницы. Пропуски и продолжение отмечаются явно; длинный/двоичный файл
не превращается в пустой успешный поиск. Чтение инструмента не расходует lifetime
budget повторно, но каждый вызов ограничен размером файла и общим числом calls.

`read_range(path, start_line, count)` возвращает до 200 строк / 8 KiB с исходными
CRLF и SHA256. Диапазоны доступны для текста до 2 MiB; `read_file` и изменение
одного файла ограничены 256 KiB. Pending-набор виден одинаково всем
инструментам. Применимые вложенные `AGENTS.md` передаются с путями/хешами как
недоверенные workflow instructions, включая явный выбор файла. Активные инструкции
не сокращаются незаметно: при нехватке окна получается явный отказ.

Снимки для executor/сессий: до 2048 UTF-8 файлов, 2 MiB на файл и 16 MiB суммарно.
Превышение/неподдерживаемое содержимое блокирует неполный snapshot. Скрытые,
служебные и запрещенные пути исключаются; binary assets/большие монорепозитории
требуют отдельного расширения. Сохранение scope snapshot не означает отправку
всего текста модели. Отбор по имени не находит все секреты
в исходном коде. Docker daemon/image должны быть доверенными. Preflight требует реально
доступных memory/swap/PID/CPU limits и default seccomp: если daemon игнорирует
эти ограничения, исполнение блокируется до запуска кода.

## Локальная история работы

`--session-db` явно разрешает сохранить выбранные исходники, задачу, предложения
и доказательства в локальной SQLite. API-ключи и environment туда не записываются.
База содержит приватный код; не добавлять ее в Git и не публиковать автоматически.
SQLite встроена в EXE через `rusqlite =0.41.1` / bundled; сервис БД не нужен.
Новая база и временные snapshot-каталоги получают private permissions на Unix.
Windows использует ACL пользовательского каталога. SQLite-транзакции сохраняют
checkpoint перед запросом модели и после каждого принятого/отклоненного действия.

```sh
lyra task --repo ./project --model /path/to/model.gguf --task-file ./TASK.txt \
  --session-db ./.lyra/tasks.sqlite --max-calls 48
lyra session list --db ./.lyra/tasks.sqlite --offset 0 --limit 20
lyra session show --db ./.lyra/tasks.sqlite --id SESSION_ID
lyra task --repo ./project --model /path/to/model.gguf --task-file ./TASK.txt \
  --session-db ./.lyra/tasks.sqlite --resume SESSION_ID --max-calls 96
lyra session show --db ./.lyra/tasks.sqlite --id SESSION_ID --report
lyra session delete --db ./.lyra/tasks.sqlite --id SESSION_ID
```

ID выводится в stderr. Resume требует тот же root и текст задания; использует
immutable snapshot, включая незакоммиченные изменения на момент старта.
Original tree при resume не перечитывается как контекст: область источников
зафиксирована snapshot, независимо от новых `--file`.
Принятые предложения и результаты сохраняются, недавняя tool-history собирается
заново чтением. Общий счетчик вызовов сохраняется; бюджет можно увеличить явно.
Optimistic revision check не допускает перезапись checkpoint другим worker.
Новая политика check_config задается пользователем при каждом запуске.
Оригинал меняется только явным apply; конфликт с внешними правками блокирует его.

Хранилище ограничено 32 MiB, отчет — 2 MiB. Удаление удаляет исходники/checkpoint
с secure_delete, но не обещает физическое стирание SSD/backup. Git worktrees,
удаление/переименование файлов и долгосрочная память остаются отдельными шагами.

## Бюджет контекста и inference

Для local task подсчет использует vocab конкретной GGUF и **тот же** chat template,
системное сообщение и выбранные skills, что передаются в inference. Ответ заранее
резервируется (`context - max_tokens`). При избытке контекста старые наблюдения
сокращаются/удаляются с provenance, новые длинные результаты и pending replacements
заменяются явными частичными данными/хешами с указанием повторного чтения. Полный
pending-код остается в report/snapshot. Task, role/permission contract и активные
project instructions не переписываются. Если обязательная часть не помещается,
`context_budget_error` завершает задачу до запроса модели. Report содержит
`prompt_budgets`; lossless deduplication — отдельный механизм, он также проверяется
по счетчику после упаковки. Это не семантическая долговременная память.

Для HTTP без доступного tokenizer используется явно помеченная оценка bytes/3,
а не обещание точного token count. Chat пока использует выбранное окно истории.
Новые defaults CLI task/свежих Desktop-настроек: context 8192, response 2048,
48 calls, 1800 s. Сохраненные пользовательские параметры не мигрируют скрыто.
Числовой сброс в настройках применяет новые defaults явно; лимит GUI — до 256 calls.

Внутри одной Session буферы native inference context выделяются один раз.
KV полностью очищается, sampler создается заново перед независимым запросом;
данные разных запросов не переиспользуются. Это не постоянный worker между
отдельными Desktop-сообщениями: после завершения CLI процесса модель освобождается.

## Desktop: проверка и продолжение

В «Помощники» можно выбрать check-config JSON, включить локальные checkpoints
и выбрать базу. Без opt-in сохранение исходников не включается. «Сохраненные
задачи…» читает страницы metadata из этой базы; продолжение использует исходный
текст задания/snapshot и текущие явно выбранные модель/provider/check config.
Счетчик calls сохраняется; для продолжения нужен явно увеличенный общий предел,
автоматического увеличения нет. API-ключи не сохраняются в snapshot.
Apply-all доступен до частичного применения набора. Кнопка recovery в заголовке
доступна независимо от наличия текущего отчета; путь фиксируется при чтении.
После recovery текущий report проекта сбрасывается, чтобы не отметить чужие
предложения примененными. Удаление checkpoints пока доступно через CLI.

## Developer eval harness

```sh
python -m unittest discover -s tools -p test_evaluate.py
python tools/evaluate.py --binary ./target/debug/lyra \
  --suite ./evals/projects/suite.json --model /path/to/model.gguf \
  --output ./.lyra/evals/run-001.json --repeats 3
```

Suite закрепляет хешами все исходники и независимый checker.
`evals/**` хранится без преобразования Git line endings, включая CRLF cases. Сначала проверяется
ожидаемый исходный провал, затем реальный local task с Docker verify, разрешенные
пути изменений, явное применение в disposable copy и повторная независимая
проверка. Код модели никогда не исполняется harness на host. Ошибки окружения
отделяются от неуспеха задачи. Результат содержит measured wall time, статус,
вызовы/отчет, SHA256 EXE/GGUF/suite; неизвестные RAM/VRAM остаются null.
Вывод содержит исходный/предложенный код и остается локальным.

Корпус содержит 36 задач с baseline/reference/per-file mutation checks;
30 проверяются на уровне функций/модулей, 6 DayZ — только структурно с открытыми
SDK/server gates. Это не доказательство качества GGUF на целевом ПК.
[Состав, проверка корпуса и подсчет метрик](EVALUATION.md).

## Размер изменений и актуальность проверки

Один набор содержит до 32 предложений и до 1 MiB их сериализованных данных.
Применение всего набора использует единый журнал восстановления. Проверка
сохраняет SHA256 точного выбранного набора исходных UTF-8 файлов с pending
изменениями. Завершение задачи и apply повторно проверяют этот набор; apply
проверяет его под блокировкой публикации до и после записи. Изменение другого
выбранного файла делает доказательство устаревшим. Последовательный apply
частей того же набора поддерживается. Это контроль выбранных байтовых входов;
он не фиксирует весь меняющийся worktree и внешние входы SDK.

Долгие задачи сохраняют последние 32 события и до 8 результатов проверок
(до 256 KiB суммарно); большие task logs сохраняют начало/конец и SHA256
захваченного вывода. Счетчики пропусков видны в отчете. Самостоятельный verify
по-прежнему ограничивает каждый поток вывода 64 KiB. Доказательства исходников
и итог выполнения не заменяются сокращенными диагностическими сообщениями.

Временный `/tmp` контейнера явно имеет `exec`: закрепленная native-проверка
должна запускать собранный Rust/C/C++ binary. Docker по умолчанию добавляет
`noexec` к tmpfs, что ломает этот сценарий. Объем tmpfs, non-root,
`nosuid,nodev`, read-only source/root и ресурсные ограничения сохраняются.
