# Обновления portable Lyra

С версии **0.2.0-dev.3** в Windows x64 CPU есть кнопка загрузки рядом с шестерёнкой
и раздел «Обновления». Как в ReplayLite: GitHub Releases, проверка SHA256,
отдельный helper, перезапуск приложения. Реализация нативная, на Rust.

## Использование

1. Для первой установки скачай полный Windows ZIP из Releases или артефакт
   `lyra-update-x86_64-pc-windows-msvc` из успешного CI. Внутри артефакта находятся
   ZIP приложения и файл `.sha256`. Полностью распакуй ZIP в доступную для записи
   папку. Сохрани `lyra-update.json` и `VERSION` рядом с обоими EXE.
2. Открой «Обновления». Автоматическая проверка включена в Windows по умолчанию:
   при открытии приложения и затем раз в 5 минут, пока окно не свёрнуто.
   Её можно отключить. Проверка не скачивает и не устанавливает пакет.
3. Для alpha-сборок включены предварительные версии. Можно выбрать только stable.
   После смены канала нажми «Проверить обновления».
4. «Скачать обновление» показывает прогресс; загрузку можно отменить. После
   проверки пакета заверши/останови задачу, сохрани нужный отчёт и выбери
   «Установить и перезапустить». Задача и отчёт в памяти не переходят в новый процесс.

CLI и inference не обращаются к сети. Только updater использует HTTPS GitHub
Releases/CDN. Ключи/аккаунт не нужны; ошибка сети или rate limit не мешает кодингу.
При отключённой проверке нет периодического таймера обновлений. Веса, CUDA Toolkit
и системный VC++ runtime updater не скачивает. Linux/CUDA-сборки обновляются вручную.
Если новых опубликованных Releases ещё нет, это обычное состояние, а не ошибка.
Артефакты Actions и черновики релизов в автоматическую выдачу не попадают.
Версии до dev.3 нужно заменить вручную: в них updater отсутствует.

## Что меняется

Только `lyra-desktop.exe`, `lyra.exe`, `THIRD_PARTY_NOTICES.txt`, `VERSION` и
`lyra-update.json`. Проекты, модели, AppData/preferences, документы/примеры и другие
файлы рядом с приложением не перезаписываются. Отдельно работающий CLI может
заблокировать замену — закрой его перед установкой. Установка не требует admin,
не меняет registry/PATH и не запускает shell.

Модифицированный/неполный установленный пакет отклоняется. Установи полный ZIP
в новую папку, если намеренно менял управляемые файлы. Для staging и backup нужно
свободное место примерно на две распакованные версии, дополнительно к загруженному ZIP.

## Проверка и восстановление

SHA256 ZIP сверяется с sidecar того же release; затем проверяются размеры и хеши
в manifest, версия каждого EXE. Это проверка целостности, **не независимая подпись
издателя**: доверие остаётся к GitHub-репозиторию и его владельцам. Authenticode
и отдельная криптографическая подпись релиза пока не реализованы.

Helper копируется в `%APPDATA%/Lyra/updater/helper-*`. Он проверяет PID, время
запуска и путь родителя, ждёт до 60 секунд и заменяет файлы только после его выхода.
Backup хранится в `.lyra-update-stage-*/backup` рядом с приложением. Новый процесс
должен отрисовать первый кадр и подтвердить версию в течение 20 секунд; иначе helper
завершает именно свой новый процесс, восстанавливает заменённые файлы и запускает
старую версию. Блокировка файлов/ошибка записи также вызывает rollback.
`%APPDATA%/Lyra/updater/last-result.json` содержит результат без кода/задания.
Успешный staging удаляется; helper-кеш убирается последующими проверками.

Замена нескольких файлов **не crash-atomic при отключении питания**. При неполном
откате backup сохраняется, ошибка указывает его путь. Закрой процессы Lyra и
скопируй все пять файлов из `backup` обратно; либо распакуй полный доверенный ZIP
в новую папку. При аварии до запуска helper может остаться `.lyra-update.lock`:
удаляй его только после проверки отсутствия helper/установки. Не удаляй backup,
пока не восстановлено приложение. Рабочие проекты при этом не затрагиваются.

## Контракт release / CI

Тег `v<Cargo.package.version>`, semver; prerelease flag соответствует суффиксу версии.
Публичные assets: `lyra-windows-x86_64.zip` и `lyra-windows-x86_64.zip.sha256`.
ZIP содержит корневые EXE/manifest/notice/VERSION и вспомогательные docs/examples.
Manifest schema 1 задаёт target `x86_64-pc-windows-msvc`, flavor `cpu`, версию и
точно четыре управляемых файла с размером и SHA256. Checksum: `<hex>  <ZIP name>`.

Лимиты: metadata 1 MiB/15 с, checksum 64 KiB/15 с, ZIP 128 MiB/600 с,
распакованный объём 256 MiB/128 записей. Переходы `..`, symlink, reparse point,
неоднозначные имена и чужие download URL отклоняются. Ненужные записи не извлекаются.

`tools/package_update.py` создаёт manifest/VERSION и update-assets. CI выполняет
native Linux/Windows tests, включая helper без графики, и открывает GUI.
Push тега после успешных проверок создаёт **draft**, не публикует его. Публикация
и smoke обновления между настоящими публичными версиями — отдельная приёмка.
Обычный push в main не создаёт релиз.
