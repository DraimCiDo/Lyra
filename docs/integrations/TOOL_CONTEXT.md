# Роли и сокращение контекста инструментов — этап 1

Это первый общий runtime-инкремент ECC/OmniRoute в PR #3. Он применяется к
задачам с инструментами, одинаково для локальной GGUF и HTTP backend.
Реализация: [роли/наблюдения](../../src/agent_runtime.rs),
[контроллер](../../src/agent.rs), [оптимизатор](../../src/context_optimizer.rs).

## Что доступно

Контроллер передаёт контракт researcher/coder/reviewer: цель, read_only и
разрешённые tools. Researcher и reviewer не видят edit tools в каталоге и
не могут получить право записи из skill или ответа модели. Все роли используют
явно выбранные навыки; произвольные новые агенты и role-specific skill bindings
относятся к следующему этапу, а не считаются уже реализованными.

Результат инструмента содержит status, summary, next_actions, artifacts и data.
Успешное предложение явно обозначено как pending: исходник ещё не изменён;
если запрос покрыт предложениями, модель должна вызвать finish. После ошибки
точной замены отклонённые old/new остаются в истории для исправления, а read_file
сообщает тип перевода строк. Предусловия точной замены и явного apply сохранены.
Это улучшение контракта, не гарантия качества любого LLM.

## Включение дедупликации

```sh
lyra task --repo ./project --model ./coder.gguf --task-file task.txt \
  --dedup-tool-context
```

Для HTTP используются прежние --provider-config/--allow/--cloud-model вместе
с тем же --dedup-tool-context. В Desktop настройка находится в
**Контекст проекта → Дедупликация результатов инструментов (задачи)**.
Для старых settings.json она выключена по умолчанию. Safe/Balanced/Aggressive
по-прежнему управляют только окном истории чата, их смысл не меняется.

Повторные успешные read_file/search/search_docs results из старой истории
заменяются result_ref. Словарь текущего запроса хранит одну точную копию либо
указывает на идентичный последний inline-результат. Он самодостаточен: никаких
несуществующих retrieve tools, внешнего хранилища или скрытого disk cache.
Последнее наблюдение всегда остаётся inline. Ошибки, task, права, tool schemas,
патчи и proposals не переписываются. Пулы из разных проектов не объединяются.

Перед отправкой оптимизатор восстанавливает исходный JSON и сравнивает его
целиком, затем проверяет уменьшение UTF-8 и JSON-escaped content bytes.
Без выигрыша или при ошибке проверки отправляется исходный запрос.
Это структурная lossless-дедупликация, не semantic compression и не полный CCR.
Модель всё равно должна уметь правильно читать ссылки, поэтому режим opt-in.

## Измерения и формат отчёта

При включении task возвращает report schema_version 3. В context_optimization
на каждый вызов есть роль, байты prompt до/после, байты сериализованного content,
число ссылок/уникальных результатов и отметка lossless_verified. CLI apply и
Desktop понимают v1/v2/v3; старые сборки не должны применять v3-отчёт.

Desktop показывает суммарное сокращение контекста в байтах. HTTP backend в
stderr/журнале сообщает request_body_bytes для фактически отправленного JSON body.
Это не полный TCP/TLS-трафик, не число токенов, не экономия оплаты и не cache-hit.
Измерения касаются одних и тех же новых контрактов с pooling off/on;
не следует сравнивать их с другим prompt/моделью и приписывать разницу сжатию.

## Проверки и следующие возможности

[Unit/golden tests](../../src/context_optimizer.rs) проверяют восстановление,
неизменность последнего результата, Unicode/CRLF, отказ на неверных ссылках,
passthrough и отсутствие сжатия ошибок/patches.
[Agent tests](../../tests/agent.rs) проверяют recovery, read_only и apply v3.
[HTTP test](../../tests/gateway.rs) сравнивает реально принятые сервером body и
восстанавливает прежний контекст. Итоги CI/приёмки — в PR #3 и
[плане этапа](../plans/0012-ecc-omniroute-stage-1.md).

Token-aware budget, RTK-фильтры, retrieval, summaries, provider prompt cache,
семантический cache и остальные engines идут отдельными этапами с corpus/quality
gates. Проценты экономии upstream не переносятся на Lyra как обещание.
