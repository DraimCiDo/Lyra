# Lyra v2 preview

Lyra v2 is an offline-first coding agent. The Windows x64 preview includes a Desktop app and CLI. Extract both executables from the same ZIP. Bring a compatible GGUF model and the Microsoft VC++ v14 x64 runtime. A Linux Docker daemon with resource limits and a locally available digest-pinned image is required for automated task checks. Local chat and proposal review work without Docker.

In `lyra-v2-desktop.exe`, select a GGUF and project (the context window follows the model's trained window unless you choose one), optionally select a check configuration, then describe a coding task. Review the diff and check output before applying. Task checkpoints use a separate `lyra-v2/tasks` directory under the OS data location. Use **Open saved task** to reopen a checkpoint after restarting. A project publication interrupted during a write retains the shared Lyra recovery journal. Use `lyra-v2 recover --repo <project>` to inspect it.

Use **Work**, **Chat**, and **Agents** in the sidebar. Each screen keeps its own draft while the window is open. In Work and Chat, use **Ctrl+Enter** (**Command+Enter** on macOS) from the composer to submit. **Settings** offers reduced motion and optional window transparency. Transparency takes effect after restarting Lyra on a desktop that supports it.

From PowerShell, choose a new path for each task checkpoint, outside the project.

```powershell
.\lyra-v2.exe task --repo C:\src\example --state C:\work\lyra-task-01 --model C:\models\coder.gguf --task "Fix the addition function" --check-config C:\work\check.json
.\lyra-v2.exe show --state C:\work\lyra-task-01
.\lyra-v2.exe apply --state C:\work\lyra-task-01
```

Use `resume` with the same state and a local model after cancellation or interruption. Without a checker, the report shows verification as skipped. With a checker, Apply requires passing evidence for the candidate, and files that change after verification can block publication. A model cannot choose a checker or run shell commands.

The preview is distributed as a separate CI artifact. The v1 release, updater and task files use their existing locations.

## Chat web search

**Web search** in Chat is off by default and applies only to the next submitted
question while enabled. It sends the current composer text (up to 500 characters)
to DuckDuckGo, without conversation history or project files. No API key is needed.
The local model selects relevant evidence IDs; Lyra displays the actual search
excerpts and clickable HTTPS source links. It does not generate a factual summary
from model memory in this mode. Source pages are not fetched, so excerpts can be
outdated or incomplete and are not independent proof that a claim is true.
No results, blocked search, network errors, invalid selections or insufficient
evidence produce an explicit inability-to-confirm reply instead of an invented
answer. An unknown name is not treated as proof that a project does not exist.
Offline Chat states that it cannot check facts online; its model answers can still
be inaccurate. Search results and links remain in memory with the conversation.
Short formatting follow-ups such as "summarize" or "А если своими словами?" reuse
the immediately preceding answer's sources without searching those words as a new
topic. This evidence mode still shows source excerpts instead of a free paraphrase.

## Import v1 data

In **Settings**, choose **Import v1 data**, select the folder with v1's `settings.json` and `conversations.json`, and review the preview before saving a v2 import file. You can reopen that file in v2, load an imported conversation from Settings in Chat, or use its model and project paths. The CLI can preview with `import-v1 --source <folder>` and save with `--into <file>`. Import keeps the original files intact. Each snapshot includes the supported data once. Cloud consent, checker settings, credentials, v1 task reports and journals stay with v1.

## Optional integrations

- Use `--reviewer` on a task to ask a read-only model reviewer to inspect the proposals. The configured checker still provides verification.
- `task-http` requires a provider registry, explicit provider and model identifiers, and `--allow-context-upload`. The selected provider receives task and workspace context. Provider configuration and credentials are supplied separately.
- Use `github-issue --repo <owner/name> --number <issue> --out <task.txt>`, then run a task with `--task-file <task.txt>`. After reviewing a proposal with a passing check, use `github-publish` with its state and the target branch and PR metadata to open a draft.
- Use `hub` to let several agents (Codex, Claude Code and local Lyra workers) work on one project at the same time, each in its own git worktree. See [Agent hub](HUB.md).
- Use `graph import` for Graphify exports, or `graph graphify` with an installed external Graphify executable for offline code extraction.

## NVIDIA CUDA

The CUDA build offers NVIDIA GPU Auto and Balanced next to the model selector. The CLI
supports `--gpu-layers 1024` for Auto, `1023` for Balanced, or an explicit layer count.
The CPU portable build rejects GPU requests. CUDA requires the NVIDIA driver and a
compatible GPU. Windows CI publishes separate CUDA artifacts for RTX 2060 (sm_75) and RTX 4060 (sm_89).

For repeatable task benchmarks, run `tools/evaluate.py` with `--protocol v2`,
the CUDA build of `lyra-v2`, and `--gpu-layers 1024 --measure-resources`.
Use a separate output file for each run configuration to compare it with CPU or Balanced.
The JSON report records the model and binary hashes, requested GPU layers, task timings
and resource samples when available.
