# Локальная модель и ресурсы ПК

## Что означает независимая работа

Inference выполняется на ПК, без аккаунта, подписки, внешнего API и отправки
кода. Веса и runtime готовятся заранее; загрузка из интернета не нужна при
каждом запуске. Использование сторонних открытых весов/runtime не является
облачным исполнением. Обучение базовой LLM с нуля — отдельная задача.

В M2 подключён CPU inference через llama.cpp; CUDA — явный feature сборки,
его исполнение пока не проверено.
`lyra doctor --json` сообщает железо текущего компьютера; неизвестные значения
равны `null`, доступные значения памяти — в байтах. `gpus: []` не доказывает
отсутствие GPU, `gpus: null` означает ошибку получения списка.
Версия схемы отчёта — 1; `inference_status: runtime_available_cpu` (или `runtime_available_cuda`)
описывает сборку, а не наличие весов/драйвера и не пригодность компьютера.

## Активный локальный тест: Qwen3.5-9B-Q4_K_M.gguf (RTX 4060)

Для настольных тестов Lyra выбран **Qwen3.5-9B-Q4_K_M.gguf**.
Точный размер зависит от изготовителя кванта, примерно 5.6–5.9 GB.
Контрольный пример текстовой модели:
[Canfield/Qwen3.5-9B-Q4_K_M-GGUF](https://huggingface.co/Canfield/Qwen3.5-9B-Q4_K_M-GGUF).
Qwen3.5 использует гибридную архитектуру Gated DeltaNet + attention; старые
llama.cpp-сборки могут не поддерживать архитектуру `qwen35`.

Новая настройка Desktop позволяет выбрать **CPU (0 слоёв)**,
**Сбалансированный (1023)**, **Авто GPU (1024)** и ручное количество
слоёв **1–1022**. Только сборка с `--features cuda` может использовать
CUDA. Стандартный Windows CI по-прежнему собирает CPU-вариант: наличие
пункта в настройках **не означает**, что CUDA доступна в таком EXE.

В режимах «Авто GPU» и «Сбалансированный» Lyra считывает `*.block_count`
из GGUF, свободную VRAM из CUDA backend, резервирует место для драйвера,
контекста и вычислительных буферов, затем оценивает безопасное число
слоёв для переноса на видеокарту. Остальные слои исполняются на CPU с
использованием системной RAM. Сбалансированный режим специально
сохраняет часть вычислений на CPU, но часто медленнее полного offload.
Это **консервативная оценка**, не гарантия от CUDA OOM: реальное
распределение весов, KV-cache и прочие буферы определяет llama.cpp.
При отсутствии CUDA Lyra не подменяет GPU-режим незаметным CPU fallback.

Начальный тест для Ryzen 7 5700X + RTX 4060 8 ГБ + RAM 32 ГБ:
- Контекст: **4096**, затем сравнить **8192**.
- Бюджет ответа: **1536 токенов**.
- CPU-потоки: **6**, затем измерить 4, 6 и 8.
- GPU: **Авто GPU** в CUDA-сборке; «Сбалансированный» только как
  альтернативный замер. Если CPU-сборка — только CPU.
- Сравнить время загрузки, скорость генерации, расход RAM и VRAM.
  Общий размер файла GGUF сам по себе не является оценкой пиковой VRAM.

CLI для CUDA-сборки:

```powershell
.\lyra.exe generate --model "D:\Models\Qwen3.5-9B-Q4_K_M.gguf" --prompt "Привет" --context 4096 --max-tokens 1536 --threads 6 --gpu-layers 1024
```

Модель может использовать thinking по умолчанию; это влияет на токены,
время и видимый ответ. Уточнение формата thinking и её отключения
необходимо тестировать отдельно. В облачном режиме Qwen3-Coder-480B
расходует ресурсы провайдера, а не локальную видеопамять.

## Первоначальный бюджет: 8 ГБ VRAM и 32 ГБ RAM

Предварительный кандидат —
[Qwen2.5-Coder-7B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct-GGUF/tree/main),
файл `qwen2.5-coder-7b-instruct-q4_k_m.gguf`, около **4,68 GB** на странице
официальных весов (примерно 4,36 GiB). Лицензия весов — Apache-2.0.
Это воспроизводимый кандидат для первого прогона, не результат сравнения
всех актуальных моделей и не подтверждение готовности к tool calling.

При 8 ГБ выделенной VRAM эта конфигурация заслуживает проверки с GPU-offload
и небольшим контекстом, начиная с **2048 токенов**. Окончательные параметры
задаются после измерения; Lyra не скачивает веса автоматически.

| Ресурс | Как учитывать |
| --- | --- |
| VRAM | Веса + KV-cache + compute buffers + драйвер/Windows/другие приложения. Размер GGUF не равен общему расходу VRAM. |
| RAM | ОС, редактор, runtime, CPU-offload и контекст; 32 ГБ не означают 32 ГБ свободной памяти. |
| CPU | Влияет на CPU inference, подготовку контекста и частичный offload; число потоков подобрать измерением. |
| SSD | Для одного кандидата нужны веса и запас на загрузку/замену; номинальная ёмкость не доказывает свободное место. |
| Контекст | Рост контекста увеличивает KV-cache и время обработки; для большого проекта нужен отбор файлов, а не весь репозиторий в одном запросе. |

Не суммировать VRAM нескольких GPU в единый гарантированно доступный пул.
Общая/интегрированная память не прибавляется к dedicated VRAM. CPU-offload
может позволить загрузку более крупной модели, но его скорость требует замера.

## Дальнейшая проверка M2

1. Выбрать и закрепить [llama.cpp](https://github.com/ggml-org/llama.cpp) либо
   подходящий локальный runtime/binding; проверить лицензию и состав поставки.
2. Явно указать локальный GGUF, проверить размер/целостность и совместимость.
   Не открывать внешний endpoint и не включать загрузку весов автоматически.
3. Измерить загрузку, peak RAM/VRAM, prompt processing, tokens/s и отмену
   на одинаковой задаче. Начать с 2048, затем сравнить 4096 токенов при наличии запаса.
4. Проверить небольшой кодинг-сценарий с известным тестом. Отдельно оценить
   качество патча и вызовы инструментов; способность продолжать текст недостаточна.
5. Повторить без доступа к интернету и при нехватке RAM/VRAM, без облачного fallback.

Windows CI проверяет CLI на виртуальном CPU-стенде. Он не измеряет RTX/CUDA,
скорость локальной модели и поведение на Windows 11 пользовательского ПК.
Личные профили и диагностические JSON хранятся в `.lyra/`, вне публичного Git.

## Пределы, которые нужно различать

- Локальный runtime не задаёт дневную квоту сообщений; работа расходует время,
  электричество и ресурсы ПК. Лицензия конкретных весов остаётся отдельным условием.
- Обученное окно модели и реально выделенное окно runtime — разные величины.
  Lyra сейчас принимает 128–32768 токенов контекста и не разрешает превышать
  `n_ctx_train` модели. Ограничение Lyra не является пределом всех локальных LLM.
- Ответ: 1–8192 токенов, по умолчанию 256; prompt ограничен 1 MiB до токенизации.
  По умолчанию окно 2048, CPU-потоки выбираются автоматически по доступному параллелизму, не более 8 (явно допустимо 1–256), таймаут 120 секунд
  (1–3600). Это параметры продукта, которые можно изменить после замеров.
- Квантизация уменьшает веса, но может влиять на качество. Длинный контекст
  дополнительно требует памяти; максимальное заявленное окно не гарантирует
  точное использование каждой детали большого проекта.
- Модель может ошибаться, повторяться, не завершить код в лимит ответа.
  Веса не учатся от каждой беседы; внешние факты и актуальный код нужны в контексте.
- Ctrl+C/таймаут проверяются между native операциями. Загрузка и один decode
  не прерываются мгновенно. RAM/VRAM не ограничены жёсткой квотой процесса;
  native/системный OOM может завершить процесс. Сохранений и правок проекта нет.
- Текущий sampler — greedy: воспроизводимый простой baseline, без настройки
  temperature/top-p. Tool calling, история чата и автоматические правки не входят в этот этап.

Передача prompt через командную строку дополнительно ограничена оболочкой и ОС (особенно Windows); предел 1 MiB не отменяет эти ограничения.
